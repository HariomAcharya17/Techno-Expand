TECHNOEXPAND - CASE STUDY NOTES
IoT-based machine failure prediction, health % and remaining useful life (RUL)
Group 47, LDRP-ITR. Project lead: Hariom Acharya.
Live demo: https://machine-prediction-live.vercel.app/

This file explains, in plain words, what is in this project, what each part does,
which models and settings were used, why, and what results they gave.


======================================================================
1. THE IDEA IN ONE PARAGRAPH
======================================================================
Machines in a factory carry IoT sensors. The readings go to the cloud every day.
A machine learning model looks at each machine's recent readings and answers:
  - How likely is it that this machine fails in the next 7 days?   (failure risk %)
  - How healthy is it right now?                                   (health % = 100 - risk)
  - Is it Healthy, Warning or Critical?                            (condition)
  - About how many days does it have left?                         (RUL, remaining useful life)
A web dashboard shows this for every machine, raises alerts, and lets a maintenance
team plan service before a breakdown instead of after it.

We had no factory hardware, so we used a public dataset of real machine readings.

3. DATASET
======================================================================
Name:     Predictive Maintenance Dataset
Author:   Himanshu Agarwal, Kaggle, MIT licence
Link:     https://www.kaggle.com/datasets/hiimanshuagarwal/predictive-maintenance-dataset
File:     predictive_maintenance_dataset.csv (6.6 MB)
Rows:     124,494 (one row = one device on one day)
Devices:  1,169
Dates:    1 Jan 2015 to 2 Nov 2015
Columns:  date, device, failure (0 or 1), metric1 ... metric9
Failures: 106 rows (0.085%). Only about 1 row in 1,170 is a failure.

Important facts we found:
  - metric1 ... metric9 are anonymised counters. We do not know what they physically measure,
    so they have no units.
  - metric7 and metric8 are exactly the same in every row, so metric8 is dropped.
  - The data is extremely imbalanced (very few failures). This decides how the model must be
    trained and how it must be judged (see section 5).

Why the CSV is not on the website: it is too large to ship and process for every visitor on the
free Vercel plan; when it was bundled the site lagged. The website only ships a small file of
precomputed results (section 6).

4. THE FIRST MODEL (v1) AND WHAT WAS WRONG WITH IT
======================================================================
Notebook: Sem6project.ipynb (first version, written with help from another AI tool)
What it did:
  - Made 3 labels: Fail = failure is 1; Medium = the row average of the 9 metrics is above the
    overall average; Healthy = everything else.
  - StandardScaler on all rows, then an 80/20 random row split.
  - RandomForestClassifier(n_estimators=200, max_depth=None, min_samples_split=2,
    min_samples_leaf=1, random_state=42, n_jobs=-1).
  - Saved model.pkl and scaler.pkl.

Result it printed: accuracy 0.9990 (99.9%).

Re-test (ml/evaluate_original.py), same pipeline, extra metrics:
                               Random split    Test machines never seen
  Accuracy                     0.9990          0.9991
  Macro F1                     0.666           0.666
  ROC-AUC (3 classes)          0.923           0.918
  Fail class precision         0.00            0.00
  Fail class recall            0.00            0.00
  Fail class F1                0.00            0.00
  Fail class ROC-AUC           0.769           0.754
  Fail class PR-AUC            0.035           0.035

So the 99.9% accuracy hid the real problem: it caught NONE of the 18 failures in the test set.

Why:
  1. The "Medium" label is not real wear. metric1 is in the hundreds of millions, so the row
     average is basically metric1. The model learned that rule: 99.6% of its decisions use metric1.
  2. With 0.085% failures, predicting "no failure" every time already gives 99.9% accuracy.
  3. Rows of the same device were in both train and test (random row split), so the test was not fair.
  4. The scaler was fitted on all rows before the split (test data leaked into training).
  5. No class weights, no tuned threshold, and each day was treated alone (no trends).
  6. Health % and RUL in the old predict.py were random numbers chosen per class.

5. MODEL v2 - WHAT WAS BUILT AND WHY
======================================================================
Notebook: ml/TechnoExpand_v2_Colab.ipynb (run in Google Colab; scikit-learn 1.6.1,
pandas 2.2.3, numpy 2.4.6). Settings: HORIZON = 7 days, RUL_CAP = 30 days, SEED = 42.

STEP 1 - Targets (labels) from real failures  [Cell 4]
  fail_within_h = 1 if the device has a recorded failure today or in the next 7 days, else 0.
      Why 7 days: gives a maintenance team time to act. 818 rows are positive.
  rul = days until the next failure, capped at 30.
      Machines with no failure ahead get 30 if their data continues at least 30 more days.
      Their last 30 days are left out of RUL training, because we cannot know what happened
      after the data ends ("censored"). 102,672 rows are usable for RUL.

STEP 2 - Features from each machine's own history  [Cell 5, function make_features()]
  For each of metric1-7 and metric9 (8 metrics):
      value today, change since yesterday (diff1),
      rolling mean and rolling max over 3, 7 and 14 days,
      7-day standard deviation (variability),
      highest value so far (cummax),
      drift since the machine's first day (dev_from_first).
  Plus day_idx (days since the machine's first reading) and record_len_so_far.
  Total: 90 features. Only past and current days are used, never future ones.
  Why: one day's reading says little; the trend before a failure says much more.

STEP 3 - Split by machine  [Cell 6, GroupShuffleSplit]
  60% train (701 machines), 20% validation (234), 20% test (234), random_state=42.
  A machine is in only one set, so test machines are truly unseen.
  Test set: 24,904 rows, 18 failing machines, 144 positive rows.

STEP 4 - Two candidate models, keep the better one  [Cell 7]
  HistGradientBoostingClassifier(learning_rate=0.05, max_iter=400, max_leaf_nodes=31,
      min_samples_leaf=40, l2_regularization=1.0, class_weight="balanced", random_state=42)
  RandomForestClassifier(n_estimators=400, min_samples_leaf=5, max_features="sqrt",
      class_weight="balanced_subsample", n_jobs=-1, random_state=42)
  class_weight="balanced" makes the rare failure rows count much more during training.
  The winner is picked on validation PR-AUC (the right score when positives are rare).
  Winner: HistGradientBoosting (gradient-boosted trees; fast, handles uneven feature scales,
  so no StandardScaler is needed).

STEP 5 - Two thresholds, tuned on validation machines only  [Cell 8]
  The model outputs a probability. Two cut-offs turn it into a condition:
    Critical if risk >= 0.8039  (the cut-off with the best F1 on validation)
    Warning  if risk >= 0.0795  (the cut-off that catches at least 60% of pre-failure days)
    Healthy  otherwise
  Using validation (not test) keeps the final test honest.

STEP 6 - Final test, done once  [Cell 9-11]
  Retrain on train + validation, keep the thresholds, score the 234 test machines.

STEP 7 - RUL model  [Cell 12]
  HistGradientBoostingRegressor(learning_rate=0.05, max_iter=400, max_leaf_nodes=31,
      min_samples_leaf=40, random_state=42)
  Rows within 30 days of a failure get sample_weight 20 (others 1), otherwise the model would
  just predict 30 for everything. Predictions are clipped to 0-30 days.

STEP 8 - Save  [Cell 14]
  failure_model.pkl, rul_model.pkl, model_config.json, metrics.json
  (backend must use scikit-learn 1.6.1 to load the .pkl files).

STEP 9 - Use  [Cell 15, function predict_machine()]
  Input: one machine's daily readings (at least ~14 days). Output:
    failure_prob_pct, health_pct (100 - risk), condition, rul_days.

6. RESULTS OF MODEL v2  (234 test machines never seen in training)
======================================================================
Source: ml/metrics_v2_colab.json (Colab run). I re-checked by loading the two .pkl files and
re-scoring the same test machines: every number matched exactly.

                               Old model (Fail class)   Model v2
  ROC-AUC                      0.754                    0.812
  PR-AUC (random guess 0.006)  0.035                    0.178
  Precision                    0.00                     0.224
  Recall                       0.00                     0.299
  F1 score                     0.00                     0.256
  Balanced accuracy            0.500                    0.646
  Accuracy                     0.999                    0.990  (not meaningful here, see below)
  Confusion matrix (v2): 24,611 true "no failure", 149 false alarms, 101 missed, 43 caught days.

For a maintenance team:
  - 10 of 18 failing machines (56%) were flagged Critical before they failed.
  - Median warning time: 6.5 days before the failure.
  - False alarms: 6.0 per 1,000 normal machine-days.
  - RUL error in the last 30 days before a failure: 11.2 days on average (MAE), RMSE 13.8 days.
    Always guessing "30 days" would be off by 16.6 days, so the model is better, but RUL is the
    weakest part.

Most useful signals (permutation importance): metric6 drift since first day, machine age
(day_idx), 7-day variability of metric2, metric4, metric7, metric7 drift, metric4 drift.

Honest limits: only 106 failures and anonymised metrics. An F1 near 0.9 is not realistic on this
data; catching more than half of the failing machines about a week early is a solid result.


======================================================================
7. WHAT THE METRICS MEAN
======================================================================
Accuracy           share of all rows predicted correctly. Misleading when failures are rare.
Precision          of all alerts raised, how many were real.
Recall             of all real pre-failure days, how many were flagged.
F1 score           one number balancing precision and recall (their harmonic mean).
ROC-AUC            how well the model ranks risky days above safe ones (0.5 = random, 1 = perfect).
PR-AUC             like ROC-AUC but focused on the rare class; random guess = share of positives.
Balanced accuracy  average of recall on each class (0.5 = no better than guessing).
Confusion matrix   counts of true negatives, false alarms, misses and catches.
MAE / RMSE         average error in days for RUL (RMSE punishes big errors more).

8. FRONTEND - WHAT THE WEBSITE USES
======================================================================
Stack: React 19, Vite 7 (build tool), Tailwind CSS 4 (styling), React Router 7 (pages),
Chart.js 4 + react-chartjs-2 (charts), react-icons (icons), SheetJS xlsx (Excel export,
loaded only when you click Export). Fonts: IBM Plex Sans and IBM Plex Mono.

How the live data works (src/sim/replay.js):
  - On load it fetches /replay.json.
  - A replay clock moves forward one day every 2 seconds (1x), or faster at 5x / 20x.
    The bar under the header has play/pause, speed and a date slider (1 Jan - 2 Nov 2015).
  - For each machine and day it looks up the real reading and the model's prediction
    (function machineAt()): status, failure risk, health, predicted RUL, actual days to failure.
  - Alerts are created when a machine moves up to Warning or Critical, and when a failure
    is recorded in the data.
  - The browser does NOT run the model. All predictions were computed once by ml/build_replay.py.

Pages:
  Overview    fleet health trend, status counts, machine table sorted by risk, recent alerts.
  Machines    cards with health, risk, predicted RUL, last reading date; filter and search.
  Machine     risk over time with the Warning/Critical lines, predicted vs actual RUL for
              machines that failed, the 8 metric channels, alert history, Excel export.
  Alerts      all alerts up to the replay date; acknowledge buttons.
  Case study  full story with all metrics, ROC curve, confusion matrices, live-vs-repo list.
  Dataset & model, System architecture, Team.

What is real and what is illustrative:
  Real:         device IDs, dates, metric readings, failures, every prediction, every metric.
  Illustrative: machine names (e.g. "CNC Milling Machine") and photos.

9. BACKEND - WHAT THE PYTHON SIDE USES
======================================================================
Stack: FastAPI + Uvicorn (web API), scikit-learn 1.6.1, pandas, numpy, joblib.
Files:
  backend/python/features.py
      make_features(data)   builds the same 90 features as the notebook.
      predict_machine(history) -> {failure_prob_pct, health_pct, condition, rul_days, days_used}
      models()              loads failure_model.pkl and rul_model.pkl once.
  backend/main.py
      POST /predict   body: JSON list of one machine's daily rows
                      [{"date": "2015-03-01", "metric1": ..., ..., "metric9": ...}, ...]
      GET  /model     thresholds, horizon, RUL cap, scikit-learn version
      WS   /ws/data   the original simulated stream from the first prototype (not used by the site now)
  backend/python/predict.py
      python predict.py history.json   (or pipe JSON into it)

How to run the backend locally:
  cd backend
  pip install -r requirements.txt
  uvicorn main:app --reload --port 8000
  Open http://localhost:8000/docs to try /predict.

Tested: three test machines gave the same result through /predict, predict.py and the full-
dataset calculation (one Critical, one Warning, one Healthy); bad input returns error 422.

11. HOW TO UPDATE EVERYTHING AFTER RETRAINING
======================================================================
1. Run ml/TechnoExpand_v2_Colab.ipynb in Colab; download the 4 files.
2. Copy failure_model.pkl, rul_model.pkl, model_config.json into backend/python/.
   Copy metrics.json to ml/metrics_v2_colab.json.
3. With scikit-learn 1.6.1 installed, run:
      python ml/build_replay.py predictive_maintenance_dataset.csv
   This rewrites frontend/public/replay.json.
4. Update frontend/src/data/caseStudy.js with the new metrics, then:
      cd frontend && npm run build
5. Commit and push; Vercel redeploys.
